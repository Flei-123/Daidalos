# Running Daidalos

Everything below was run on this checkout, in this order. Commands are relative
to the project root.

Every number in this file was measured on the tree at commit `761bd29` plus the
modifier round's working changes, which is this file's parent - the two commits
differ in RUN.md alone, because a document cannot contain the hash of the commit
that contains it. The output the numbers come out of is `build/last_run.log`,
written by `./build.sh` and appended to by `./tools/run_tests.sh`, and
`build/last_win.log`, written by `./build_win.sh`. Neither is in git (`build/`
is ignored); both are regenerated by the commands below.

## 1. Build

```bash
./build.sh
```

One script, no cmake step, no generator. It compiles the engine core, the three
physics backends, the renderer, the drone show pipeline, ~40 test binaries, the
tools and the examples, and it RUNS the parts that are claims rather than code:
the two leak tests (no Talos header outside `src/physics_talos.cpp`, no Vulkan
symbol outside `src/rhi_vulkan*`), the drone show suite with its determinism
proof and its scaling table, and the screenshot tool.

Roughly 6 minutes from cold on 8 cores (`rm -rf build && ./build.sh`, measured
here), and it ends in `-- ok`. Everything it prints also lands in
`build/last_run.log` - the compile lines, the leak tests, the drone show suite
with its scaling table, the screenshot tool's log - so every number quoted below
can be read back out of the file the command wrote rather than believed.

It stops at the first failure: every "compile,
then run" step is two statements rather than `g++ ... && ./binary`, because
under `set -e` the left side of an AND-list is exempt from errexit - which is
how this checkout once finished green while running a test binary from the day
before. It needs `g++` (C++17), the Vulkan
headers and `glslangValidator`; without them the renderer section is skipped and
everything else still builds. Optional, auto-detected next door: Talos
(`/root/projects/talos`), Jolt, Aulos, Mnemosyne, QuickJS.

Useful variants:

```bash
./build.sh noaudio          # without Aulos
DAI_WINDOW=wayland ./build.sh
DAI_WINDOW=win32 ./build.sh # cross compile check with mingw-w64
```

### The Windows build

```bash
./build_win.sh              # -> build-win/*.exe, whole output in build/last_win.log
```

A full cross compile with mingw-w64, not a syntax check: every `src/*.cpp` the
editor needs is compiled again with `x86_64-w64-mingw32-g++-posix`, the shaders
are embedded, and `build-win/editor_demo.exe` is linked. It is run after the
headers this round touched - `include/dai_blockout.h`,
`include/dai_blockout_csg.h`, `include/dai_blockout_host.inl` and the
`src/dai_editor_ui*.inl` files - because a header that only Linux g++ ever sees
is a header that compiles on one compiler. It ends in:

Those lines are not typed into this file: `tools/run_tests.sh` reads them back
out of `build/last_win.log` at the end of every run and writes them between the
two markers above, and a `RUN.md` that still carries a placeholder turns the run
red. The log is written by `./build_win.sh` itself, in the same run that links
the exe - the script pipes its own output through `tee build/last_win.log` the
way `tools/run_tests.sh` does, so there is no second command anybody can forget.
The date in the block is that file's own timestamp, and `tools/run_tests.sh`
turns RED when the log is older than `build-win/editor_demo.exe` or older than
anything in `include/` or `src/`: a receipt for a build that no longer describes
the checkout is worse than no receipt. A quoted log line that somebody has to remember to update is
a quoted log line that is wrong by the next round - this one was, and said
`WIN_TAIL_PLACEHOLDER` out loud.

export - the .skyc, read back and flown, is flyable

0.400 m is the fault the fixture PLANTS on purpose - two points parked 0.4 m
apart inside one formation, which no transition can undo (see `[3i]`). The
assertion is that this is the only pair in 420 that ever goes below the 2 m
minimum anywhere on the timeline, that the flight never makes it worse than the
formation already is, and that nothing exceeds 8 m/s or 4 m/s². A fixture
without that planted fault would prove that the audit runs, not that it
measures.

### The scaling table, as measured

Not a claim, a run. This is what `./build/test_droneshow` printed here on the
run this file documents, so a reader can tell a regression from a faster
machine:

| when | commit | machine |
|---|---|---|
| 2026-08-14 | `d4bf8df` | AMD EPYC 7571, 8 cores, 12 GB, Debian 12, g++ 12.2, `-O3`, and other builds running next to it |

| drones | sample | assign | layer | profile | validate | plan MB | check MB | ticks | wall |
|---:|---:|---:|---:|---:|---:|---:|---:|---:|---:|
| 100 | 17.12 ms | 2.16 ms | 1.19 ms | 0.00 ms | 11.23 ms | 0.01 | 0.02 | 701 | 32 ms |
| 1 000 | 94.17 ms | 447.74 ms | 13.32 ms | 0.07 ms | 168.95 ms | 0.14 | 0.21 | 946 | 724 ms |
| 10 000 | 1 070.47 ms | 362.17 ms | 2 332.73 ms | 1.00 ms | 4 390.36 ms | 1.87 | 2.44 | 2 437 | 8 159 ms |

Read it with the tick column in hand: the fixture's figures grow with the fleet,
so the 10,000 drone show is also longer than the 1,000 drone one, and part of
the wall clock difference is show length rather than fleet size. The test
therefore compares the two rows PER TICK - (8159/2437) / (724/946) = **4.37 x**
for ten times the drones, on the tree at `d4bf8df` - and fails the
build above 15 x, or above 30 s of wall clock for the big row (`tests/test_droneshow.cpp`,
the two CHECKs after the table). A quadratic tick would put ten in that ratio on
its own; a cubic assignment a hundred. An earlier run of the same table on an
idle machine came out at 3.79 x (8243 ms for the big row instead of 8159); the
spread between those two numbers is three builds sharing eight cores, and it is
the reason the bound is three times the measurement rather than a whisker above
it.

`assign` falling from 448 ms to 362 ms between the two big rows is not a typo:
above 2,000 drones the solver switches from the exact Jonker-Volgenant to the
clustered auction, and the storyboard says so in the panel.

The memory columns are the point of the whole keyframe design: 10,000 drones
over 2,437 ticks are 1.87 MB of plan. Materialised ticks would be 3 433 MB,
which the suite prints next to it:

```
[3f] the plan is keyframes, and it stays keyframes
  plan for 10000 drones x 8 keys: 1.87 MB (materialised ticks: 3433 MB)
```

Both numbers move with the machine. The two things that must not move are the
determinism proof (`determinism - the same input, twice, byte for byte`, a
`memcmp`, not an epsilon) and the zero in the failure count.

## 3. The editor

```bash
DAI_SHADER_DIR=shaders ./build/editor_demo
```

X11 only for now (it reads keysyms directly). On a machine with no display,
`Xvfb :77 -screen 0 1600x900x24 &` and `DISPLAY=:77` in front of it.

The Project panel picks or creates a project, and creating one asks for the
**kind**: `game` or `droneshow`. That single field is what swaps the panel set -
the same binary, the same dock, the same renderer. A project file written before
the field existed has no `kind` line and opens as a game, unchanged.

## 4. A drone show without the editor

The screenshot tool is also the shortest end-to-end run of the show pipeline:
it creates a game project and a droneshow project side by side, re-opens both
from disk, samples three figures, solves, validates, exports `.skyc`, `.csv` and
`.json`, and writes ten PNGs of the panels.

```bash
mkdir -p .gauntlet-shots
DAI_SHADER_DIR=shaders ./build/droneshow_shot .gauntlet-shots 1600 900
# the same show at two other window sizes, into names of their own
DAI_SHADER_DIR=shaders ./build/droneshow_shot .gauntlet-shots 1100 700  narrow-
DAI_SHADER_DIR=shaders ./build/droneshow_shot .gauntlet-shots 1920 1080 wide-
```

All three run inside `./build.sh`, so `.gauntlet-shots/` is a product of the
build and not of somebody's shell history. The fourth argument is the SET: with
no dash it is a prefix (`narrow-03-viewport-conflict.png`), with a leading dash
a suffix, and left off the pictures keep the plain names. The ten per set are
`01-start`, `02-transition`, `02b-ring-formation`, `02c-cube-formation`,
`03-viewport-conflict`, `04-validation`,
`07-preview-full`, `08-conflict-clicked`.

It is idempotent: run it twice and it opens the projects it made the first time.
The projects land in `build/shot_projects/`, the exports in that project's
`assets/`. It prints what it photographed, including the conflict it clicked:

`02-transition` is the picture that has to show a fleet in FLIGHT, so its moment
is computed rather than typed: figure 2 is reached at `t_start = 36.11 s` and
the move into it takes `36.11 - (0.00 + 4.00) = 32.11 s`, so the shutter opens
at the middle of it, 20.05 s. The tool measures the claim instead of making it -
at that instant the average drone is 8.3 m away from the shape it left and
11.9 m from the one it is flying to, both printed above. It used to be a hard
coded 10.5 s, which the solver invalidated the first time a transition was
stretched to hold `v_max`: the picture showed a fleet standing still in the
first figure and was captioned "mid transition".

`02b` and `02c` are the two figures that move is between, STANDING - the ring
and the cube in the middle of their own hold, at `t_start + hold/2` out of the
same solved plan. A cloud of drones in transit proves the show moves; it does
not prove the sampler puts drones on a shape, and that is what these two are for.

The solve does not say "ok", and that is the fixture working as intended: it
plants faults, because a validation panel photographed with an empty list proves
nothing about the panel that has to show one. The fourth figure has two points
parked 0.40 m apart, which no transition can undo, so `dai_show_layer` answers
`DAI_SHOW_LAYER_FORMATION_FAULT` rather than `DAI_OK` and `dai_show_solve`
passes it on with the pair, the gap and the figure it stands in - reporting a
show as solved on the strength of `0 unresolved` was exactly the hole that
answer closes. Drone 173 is the point that was moved; 172+216 is the pair the
validator then finds standing together at 80.60 s. The fifth figure breaks two
OTHER rules - one point over the ceiling, two parked inside the floor - so the
list in `04-validation.png` has three rows of two kinds to sort, select and
scroll, which is what makes it a list rather than a row.

That second figure is deliberately the ugly one, and the run above says so in
its first line: `solve 1 transition conflicts could not be separated`. That one
is listed, timestamped and clickable rather than swallowed - which is the
behaviour this file documents. The panel prints the same thing as a set of
counters (`N crossings: N lifted, N delayed, N left over, N formation faults`),
and those counters are readable in the editor's own Settings panel rather than quoted here,
because a number that only a screenshot can prove does not belong in a
paragraph that claims to be a transcript. The show the FLIGHT PROOF is taken of is the one in
`[3g]`/`[6e]`, which carries the 0.40 m plant and nothing else.

The narrow run exists because 1100x700 is where labels collide if a panel lays

### The modifier stack

A list of operators that lives as DATA on the node - serialised with the scene,
undoable, reorderable, each one switchable - and is evaluated on the blockout
or CSG mesh the node already has. Five types: `Bevel`, `Subdivide`, `Solidify`,
`Array`, `Mirror`. The geometry is in `include/dai_modifier_edge.h` (bevel,
subdivide) and `include/dai_modifier_dup.h` (solidify, array, mirror); the
stack, its scene lines and its property names are in `include/dai_doc.h` and
`src/dai_doc_text.cpp`; the inspector list is in
`src/dai_editor_ui_blockout_inspector.inl`. `docs/BLOCKOUT.md` has the field by
field description and the property name scheme.

The suites are `tests/modifier_bevel_cases.hpp` (in `test_doc`),
`tests/modifier_dup_cases.hpp` (in `test_fracture`) and
`tests/modifier_stack_cases.hpp` (in `test_editor_ui`). They measure rather
than assert - these lines are `./build/test_doc` and `./build/test_fracture`
verbatim:

```
-- modifiers: bevel and subdivide --
  chamfer: 26 faces and s^3 - 6*b^2*s + (16/3)*b^3 at 0.05, 0.10, 0.20 m
  the chamfer follows the shape: 6, 24 and 96 face cubes agree to 1e-6
  segments 1..4: the chamfer rounds off and the volume climbs back
  the doorway takes a chamfer: closed, no slivers, and 18.2*b^2 m3 lighter
  flat subdivision: 24, 96, 384 faces and the volume to the last digit
  Catmull-Clark: inside the cube, outside its own ball, tighter every level
  determinism: 2928 vertices and 2928 indices, bit identical, twice each
```

```
[dup 2] array - one thing, n times
  2..5 copies at 1.5 m: n x the triangles, n x the volume, (n-1) x 1.5 m longer
[dup 3] mirror - half a thing is the thing
  half a box on X, Y and Z: symmetric to 1e-5, closed, 20 triangles
[dup 5] on a boolean - the wall with a doorway in it
  10 mm skin on the cut wall: 0.236002 m3 against 23.600000 m2 x 0.01
```

Order counts and is tested both ways round: solidify then array then mirror
spans 5.400 m, the other order 4.200 m.

The bridge reaches the stack through the same property names, so a script sets
a modifier without a mouse - `examples/scripts/modifier_stair.js` builds a
stair from one slab with Bevel plus Array, and `tools/bridge_check.py` sets
`modifier.count`, `modifier.0.type`, `modifier.0.copies` and `modifier.0.offset`
over the socket, then proves the rendered picture changed and that one undo
takes the parameter back while the node stays.

## What the drone show suite does NOT yet prove

Everything above is a measurement. This section is the other half of an honest
receipt: three places where a test says more than it checks. They are written
down rather than fixed because a known gap in a test is a bug in the test, and a
reader who is told about it can weigh the green total correctly.

* **The photographed show and the tested show are not the same show.**
  `tools/droneshow_shot.cpp` builds FIVE figures - three shapes, a near miss and
  an out-of-bounds cube. The fixtures in `tests/droneshow_cases_plan.cpp` (`[3g]`)
  and `tests/droneshow_cases_io.cpp` (`screenshot_show`) build FOUR: they stop
  before the fifth. Both call themselves "the show the screenshots are taken
  of", and neither is. Concretely, the `unresolved == 0` assertion in `[3g]`
  never covers the show whose status bar reads `1 left over`. The fix is not to
  copy the fifth figure into two more files - the numbers already sit in three
  places and the fence limit differs between them (the show default is 150 m,
  the project default 120 m, which is why the tool prints a 120 m ceiling and
  the tests use a 150 m one). The fix is ONE fixture builder that the tool and
  both suites call.

* **The flight proof identifies the planted pair by its gap.**
  `tests/droneshow_cases_io.cpp` `[6e]` finds the deliberately broken pair with
  `fabs(sep - 0.4) < 0.02`, and `tests/droneshow_cases_plan.cpp` says in its own
  comment why that is unsound: a foreign pair that the layering happens to push
  to 0.40 m is then accepted as the planted one, and that pair is precisely the
  bug the case exists to find. `plan.cpp` already does it correctly, by tracing
  the assignment back out of the plan (`trace_points_to_drones`); that function
  is local to one file and has to be shared through `tests/droneshow_cases.hpp`
  before `[6e]` can use it. The `planted_seen == 1` check limits the damage - two
  pairs at 0.40 m fail the case - but it does not close the hole.

* **The gizmo and the brush are proved as INPUT, not as a picture.**
  `tests/test_editor_ui.cpp` grabs the X handle where `dai_show_ui_gizmo_handle`
  says the panel drew it, drags it sixty pixels and checks the figure moved in X
  and in nothing else; the brush is clicked over the preview and the painted
  points are counted. That covers the arithmetic and the hit testing. It does
  NOT cover whether the handle is legible against a bright figure, whether the
  three colours are distinguishable, or whether the new Figure section in the
  inspector fits the panel at every width. Those are answers only a screenshot
  gives, and the screenshots in `.gauntlet-shots/` are taken with the pointer
  parked outside the preview, so no shot in this repository has a gizmo being
  dragged in it.

* **Nothing here proves a real drone flies.** The whole suite is a proof about
  a FILE: the plan, the export and the reimported trajectories. Whether an
  aircraft can follow them is a question about thrust, wind and the flight
  controller, and no assertion in this repository touches it.

## If something fails

* **`glslangValidator: not found`** - the renderer, the editor, the show panels
  and the screenshot tool are skipped; the engine, the pipeline and the headless
  suites still build and run.
* **`error: XDG_RUNTIME_DIR is invalid or not set`** - printed by the Vulkan
  loader, harmless: the renderer draws offscreen and never asks for a
  compositor.
* **`cannot find -lJolt`** - only the reference backend. `WITH_JOLT=` unset or
  `JOLT_LIB=` pointing elsewhere builds without it.
* **the build ends in `ld terminated with signal 15`** - the build was killed
  from outside (a timeout, usually). It is not a link error; run it again with
  more time.
